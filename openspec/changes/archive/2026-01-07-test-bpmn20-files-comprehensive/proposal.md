# Proposal: test-bpmn20-files-comprehensive

## Summary
为 `process/convert/` 目录下的所有 `.bpmn20.xml` 文件建立完善的测试体系，确保 vue-flow 显示效果与 bpmn-js 高度一致，并验证双向转换功能的正确性。

## Background
当前项目已实现基础的 BPMN 导入导出功能，包括：
- BPMN XML → vue-flow JSON 转换（导入）
- vue-flow JSON → BPMN XML 转换（导出）
- 基础测试页面和测试工具

`process/convert/` 目录包含 7 个 `.bpmn20.xml` 测试文件，这些文件涵盖了各种 BPMN 2.0 场景：
1. **collapsed-subprocess.bpmn20.xml** - 包含折叠子流程、文本注释和关联
2. **extensions.bpmn20.xml** - 包含 Flowable 和自定义扩展元素
3. **eventlistenerscript.bpmn20.xml** - 包含脚本任务监听器
4. **eventlistenersmodel.bpmn20.xml** - 事件监听器模型
5. **extensionsXmlLocation.bpmn20.xml** - 扩展 XML 位置
6. **ProcessWithCompensationAssociation.bpmn20.xml** - 补偿关联处理
7. **servicetaskfailedjobretrytimecyclemodel.bpmn20.xml** - 服务任务失败重试配置

然而，当前缺少对这些复杂场景的系统性测试，无法保证：
- vue-flow 的渲染效果与 bpmn-js 一致
- 双向转换（往返转换）保持数据完整性
- 扩展属性正确处理
- 边界情况得到妥善处理

## Why
需要完善测试体系的原因：

1. **质量保证**：这些 `.bpmn20.xml` 文件来自真实的 Flowable/Camunda 测试集，代表了实际生产环境中的复杂场景
2. **用户体验一致性**：用户期望在不同工具（bpmn-js vs vue-flow）中看到相同的流程图
3. **数据完整性**：双向转换不应丢失或错误处理任何数据
4. **扩展兼容性**：Flowable/Camunda 扩展属性是企业级应用的关键功能
5. **回归预防**：未来代码修改不会破坏现有功能

## What Changes
本变更将建立一个全面的测试体系，包括：

### 1. 自动化测试套件
- 为每个 `.bpmn20.xml` 文件创建对应的测试用例
- 验证导入、导出和往返转换的正确性
- 对比 vue-flow 和 bpmn-js 的渲染输出

### 2. 视觉回归测试
- 自动化截图对比工具
- 检测布局、位置、标签等视觉差异
- 生成可读的差异报告

### 3. 扩展属性测试
- 验证 Flowable/Camunda 扩展的导入导出
- 确保自定义命名空间正确处理
- 测试复杂的扩展结构（如 script、field 等）

### 4. 边界情况测试
- 折叠/展开的子流程
- 多层嵌套的流程
- 文本注释和关联
- 条件表达式和监听器

### 5. 性能基准测试
- 测量转换和渲染时间
- 确保大型流程文件在合理时间内处理完成

### 6. 测试报告和文档
- 生成测试覆盖率报告
- 记录已知限制和问题
- 提供测试结果可视化

## Success Criteria
变更成功的标准：

1. **所有 7 个 `.bpmn20.xml` 文件都有对应的测试用例**
2. **至少 90% 的测试用例通过**（已知限制可标记为 pending）
3. **往返转换测试验证关键属性的完整性**
4. **视觉回归测试检测到明显差异时自动失败**
5. **测试套件可在 CI 环境中自动运行**
6. **生成清晰的测试报告，便于问题定位**

## Alternatives Considered

### 1. 仅手动测试
- **优点**：快速实现，无需编写测试代码
- **缺点**：无法自动化，容易遗漏问题，难以回归
- **拒绝原因**：不利于长期维护和质量保证

### 2. 仅使用现有的简单 fixture
- **优点**：测试简单快速
- **缺点**：无法覆盖复杂场景，难以发现实际问题
- **拒绝原因**：`.bpmn20.xml` 文件的价值在于其复杂性

### 3. 分阶段实现（本次仅实现部分测试）
- **优点**：降低一次性工作量
- **缺点**：测试覆盖不完整，可能推迟发现问题
- **拒绝原因**：一次性建立完整的测试体系更高效

## Dependencies
- 依赖现有的 `bpmn-testing` spec 中定义的测试工具和辅助函数
- 依赖现有的 `bpmn-xml-import` 和 `bpmn-conversion` specs
- 需要安装或开发视觉回归测试工具（如 Playwright 的截图对比功能）

## Risks and Mitigations

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 某些 `.bpmn20.xml` 文件包含不支持的元素 | 测试失败 | 将这些测试标记为 pending，记录为已知限制 |
| 视觉对比产生大量误报 | 维护成本高 | 配合合理的容差阈值，支持手动审核 |
| 测试执行时间过长 | CI/CD 变慢 | 将性能测试标记为 `@slow`，在 CI 中选择性运行 |
| bpmn-js 和 vue-flow 的渲染差异固有存在 | 无法完全一致 | 关注功能一致性而非像素级一致，允许合理的视觉差异 |

## Out of Scope
以下内容不在本变更范围内：
- 修复转换逻辑中的 bug（仅记录问题，修复作为独立任务）
- 添加对不支持的 BPMN 元素的支持（如新的网关类型）
- 性能优化（仅测量性能，不进行优化）
- 用户界面改进（仅测试现有界面）

## Open Questions
1. 是否需要为每个测试文件生成详细的差异报告，还是仅通过/失败？
   - **建议**：对失败的测试生成详细报告，通过的测试仅显示统计信息
2. 视觉对比的容差阈值应该如何设置？
   - **建议**：从较宽松的阈值开始，根据实际运行结果调整
3. 是否需要在测试失败时自动截图保存？
   - **建议**：是，保存失败时的截图以便调试
